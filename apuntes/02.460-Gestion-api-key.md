# Cómo guardar API keys

Una API key es una credencial: una cadena de texto que identifica y autoriza a tu programa frente a un servicio externo (Gemini, Anthropic, OpenAI, etc.). Quien tiene la key puede usar el servicio **a tu nombre y a tu costo**. Por eso el problema no es técnico sino de *secreto*: ¿dónde guardamos algo que el programa necesita leer pero que nadie más debería ver?

> La regla de oro: **una API key nunca va escrita en el código fuente**. Si está en el código, viaja con el código. Y el código termina en GitHub, en un repo compartido, en la pantalla de un proyector durante una clase. Una vez expuesta, la key está comprometida para siempre.

## El problema, desde el principio

Imaginá la solución ingenua:

``` csharp
// MAL. Nunca hagas esto.
string apiKey = "AIzaSyD-1234567890abcdefg";
```

Esto funciona. El programa anda. Pero acabás de meter un secreto dentro de un archivo que vas a versionar con Git y subir a GitHub. Bots automáticos escanean GitHub buscando exactamente este patrón, y en cuestión de minutos alguien puede estar gastando tu cuota.

La idea central para resolverlo es **separar la configuración del código**. El código describe *qué hacer*; la configuración (incluida la key) describe *con qué credenciales y en qué entorno hacerlo*. El programa, en tiempo de ejecución, lee la key desde un lugar externo que vive *fuera* del repositorio.

Ese "lugar externo" tiene varias formas. Las vemos de la más fundamental a la más cómoda.

## Variables de entorno

Una **variable de entorno** es un par `NOMBRE=valor` que el sistema operativo le entrega a cada proceso cuando arranca. Es el mecanismo más antiguo y universal: existe en Windows, Mac y Linux, y todo lenguaje sabe leerlas. No dependen de tu proyecto ni de tu lenguaje; viven en el sistema operativo.

Cuando tu programa arranca, hereda una copia de las variables de entorno del proceso que lo lanzó (la terminal, el IDE). Por eso, si definís una variable en una terminal, solo los programas lanzados *desde esa misma terminal* la verán.

Leerlas en C# es directo:

``` csharp
string apiKey = Environment.GetEnvironmentVariable("GEMINI_API_KEY");
```

> Fijate que el código ya no contiene el secreto: contiene el *nombre* de dónde buscarlo. El código es público, el valor es privado.

### En Windows

En PowerShell hay dos niveles. El primero es temporal: la variable vive solo mientras esa ventana de terminal esté abierta.

``` powershell
# Solo para la sesión actual de esta terminal
$env:GEMINI_API_KEY = "tu-key-aca"
```

El segundo es persistente: queda guardada en el registro de Windows para tu usuario, y estará disponible en todas las terminales futuras.

``` powershell
# Persistente para tu usuario (sobrevive reinicios)
[Environment]::SetEnvironmentVariable("GEMINI_API_KEY", "tu-key-aca", "User")
```

Después de la versión persistente tenés que **cerrar y reabrir** la terminal (y a veces el IDE) para que tome el cambio, porque las variables se heredan en el arranque del proceso.

También podés hacerlo por interfaz gráfica: buscá "Editar variables de entorno del sistema" en el menú inicio.

Para **averiguar qué hay guardado** listás todas las variables o leés una puntual:

``` powershell
# Listar todas
Get-ChildItem Env:

# Ver una sola
$env:GEMINI_API_KEY
```

Para **borrar**, distinguí los dos niveles. La de la sesión actual se borra asignándole `$null`; la persistente se borra pasándole `$null` al mismo método con que la creaste:

``` powershell
# Borrar de la sesión actual
$env:GEMINI_API_KEY = $null

# Borrar la persistente del usuario (registro)
[Environment]::SetEnvironmentVariable("GEMINI_API_KEY", $null, "User")
```

### En Mac (y Linux)

En la terminal, lo temporal se hace con `export`:

``` bash
# Solo para la sesión actual de esta terminal
export GEMINI_API_KEY="tu-key-aca"
```

Para hacerlo persistente, agregás ese mismo `export` al archivo de configuración de tu shell. En Mac moderno el shell por defecto es **zsh**, así que el archivo es `~/.zshrc` (si usás bash, sería `~/.bashrc`):

``` bash
# Agregar al final de ~/.zshrc
echo 'export GEMINI_API_KEY="tu-key-aca"' >> ~/.zshrc
source ~/.zshrc   # recarga el archivo sin reabrir la terminal
```

Ese archivo se ejecuta cada vez que abrís una terminal nueva, así que la variable queda disponible siempre.

Para **averiguar qué hay guardado** listás o leés una puntual:

``` bash
# Listar todas (o filtrar con grep)
printenv
printenv | grep GEMINI

# Ver una sola
echo $GEMINI_API_KEY
```

Para **borrar** de la sesión actual usás `unset`. Pero ojo: si la hiciste persistente agregándola al `~/.zshrc`, `unset` solo la saca de la terminal actual; **vuelve a aparecer** la próxima vez que abras una terminal. Para borrarla de verdad tenés que editar el `~/.zshrc` y eliminar la línea del `export`.

``` bash
# Borrar de la sesión actual
unset GEMINI_API_KEY

# Borrar la persistente: abrir el archivo y eliminar la línea export
nano ~/.zshrc
source ~/.zshrc   # recargar para que tome el cambio
```

> Moraleja: borrá del *mismo lugar* donde guardaste. Si la persististe en un archivo de configuración, `unset` no alcanza; hay que tocar el archivo.

## El archivo `.env`

Las variables de entorno persistentes tienen un problema práctico: son globales a tu usuario, no a tu proyecto. Si trabajás en cinco proyectos con cinco keys distintas, ensuciás el sistema entero y se vuelve difícil saber qué necesita cada proyecto.

La convención **`.env`** resuelve esto. Es simplemente un archivo de texto, en la raíz del proyecto, con las variables que ese proyecto necesita:

``` env
GEMINI_API_KEY=tu-key-aca
DB_CONNECTION=Data Source=app.db
```

La key sigue estando *fuera del código*, pero ahora vive *junto al proyecto* y es fácil ver de un vistazo qué credenciales requiere.

> El punto crítico: el archivo `.env` **nunca se versiona**. Por eso lo primero que hacés es agregarlo al `.gitignore`.

``` gitignore
# .gitignore
.env
```

La práctica habitual es versionar un `.env.example` con los *nombres* de las variables pero sin los valores, para que otro desarrollador sepa qué tiene que completar:

``` env
# .env.example  (este SÍ se versiona)
GEMINI_API_KEY=
DB_CONNECTION=
```

En el ecosistema .NET, el `.env` no se lee solo: un paquete como `DotNetEnv` carga ese archivo y vuelca su contenido a las variables de entorno del proceso al arrancar.

``` bash
dotnet add package DotNetEnv
```

``` csharp
DotNetEnv.Env.Load();  // lee .env y lo carga como variables de entorno
string apiKey = Environment.GetEnvironmentVariable("GEMINI_API_KEY");
```

Así cerramos el círculo: el `.env` alimenta a las variables de entorno, y el código lee variables de entorno como siempre.

Acá **averiguar qué hay y borrar** es lo más simple de todo: el `.env` es un archivo de texto. Ver qué contiene es abrirlo; borrar una key es eliminar (o vaciar) su línea y guardar. No hay registro escondido ni magia.

``` bash
cat .env          # ver qué hay
nano .env         # editar y borrar la línea que quieras
```

## La forma específica de .NET: User Secrets

.NET trae su propia solución, pensada justamente para no andar con `.env` en desarrollo: el **Secret Manager** (User Secrets). La idea es elegante: guarda los secretos en un archivo JSON **fuera de la carpeta del proyecto**, en tu perfil de usuario. Así es *físicamente imposible* commitearlo por accidente, porque no está dentro del repo.

Lo activás una vez por proyecto:

``` bash
dotnet user-secrets init
```

Esto agrega un `<UserSecretsId>` (un GUID) a tu archivo `.csproj`. Después guardás cada secreto:

``` bash
dotnet user-secrets set "GeminiApiKey" "tu-key-aca"
```

El valor se guarda en un `secrets.json` ubicado en:

- **Windows**: `%APPDATA%\Microsoft\UserSecrets\<id>\secrets.json`
- **Mac/Linux**: `~/.microsoft/usersecrets/<id>/secrets.json`

Para leerlo, .NET integra User Secrets en el sistema de **configuración** (`IConfiguration`). En desarrollo, el secreto se mezcla automáticamente con `appsettings.json`, variables de entorno, etc.:

``` csharp
var builder = WebApplication.CreateBuilder(args);
string apiKey = builder.Configuration["GeminiApiKey"];
```

> Por qué esto es lo idiomático en .NET: el código pide `Configuration["GeminiApiKey"]` sin saber *de dónde* sale el valor. En tu máquina sale de User Secrets; en el servidor de producción saldrá de una variable de entorno o de un servicio como Azure Key Vault. El código no cambia: cambia solo la *fuente* de configuración según el entorno.

Para **averiguar qué hay y borrar**, el Secret Manager tiene comandos propios, que es una de sus ventajas frente a las variables de entorno:

``` bash
# Listar todo lo guardado en el proyecto
dotnet user-secrets list

# Borrar uno por su clave
dotnet user-secrets remove "GeminiApiKey"

# Borrar todos los del proyecto
dotnet user-secrets clear
```

> Recordá que estos comandos operan sobre el `secrets.json` asociado al `<UserSecretsId>` del `.csproj`. Si los corrés desde otra carpeta de proyecto, vas a estar mirando otros secretos (o ninguno).

## En resumen

| Mecanismo | Alcance | Cuándo usarlo | Cómo borrar |
|------------------|------------------|------------------|------------------|
| Variable de entorno | Sistema / usuario | Universal, producción, scripts | `$env:X=$null` / `unset` o editar `~/.zshrc` |
| `.env` + DotNetEnv | Por proyecto | Desarrollo, equipos, multi-lenguaje | Eliminar la línea del archivo |
| User Secrets | Por proyecto (fuera del repo) | Desarrollo en .NET, lo idiomático | `dotnet user-secrets remove` / `clear` |

Las tres comparten el mismo principio fundamental: **el secreto vive fuera del código y fuera del control de versiones**, y el programa lo lee en tiempo de ejecución. La diferencia está en la comodidad y en qué tan difícil es equivocarse y exponerlo.
