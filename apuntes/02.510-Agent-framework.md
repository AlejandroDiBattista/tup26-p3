> Tutorial conceptual para Programación III · C# 14 / .NET 10

## Antes de empezar: el porqué

Hay una pregunta que conviene contestar antes de tocar una sola línea de código: **¿qué problema resuelve un framework de agentes que no resuelva ya un cliente de chat?**

Cuando usás `IChatClient` (la abstracción de MEAI que ya vimos en clase), el flujo es lineal y vos sos el dueño del bucle:

```
vos → armás mensajes → modelo responde → vos leés la respuesta → vos decidís qué hacer
```

Si el modelo quiere usar una herramienta, *vos* tenés que detectar el pedido, ejecutar la función, volver a meter el resultado en la conversación y reinvocar. Si querés que se acuerde de la charla anterior, *vos* acumulás los mensajes. Si querés que varios modelos colaboren, *vos* coordinás todo a mano.

Eso es exactamente lo que hicimos cuando construimos el loop ReAct "a mano": funciona, pero todo el andamiaje queda a tu cargo.

Un **agente** invierte esa relación. En vez de que vos manejes el bucle, le pasás un objetivo y *él* decide:

```
vos → le das un objetivo → el agente razona, elige herramientas,
       las ejecuta, evalúa resultados, decide el próximo paso → te devuelve el resultado
```

El Microsoft Agent Framework (MAF de ahora en más) no es magia nueva: es **el bucle ReAct que ya escribiste, pero industrializado**. Te da, listos para usar, los cuatro andamiajes que antes hacías a mano:

1. **El bucle de ejecución** (modelo → herramienta → modelo → ...) hasta terminar.
2. **El estado de la conversación** (memoria de corto plazo, dentro de una sesión).
3. **La inyección de contexto** (memoria de largo plazo y RAG, entre sesiones).
4. **La orquestación de varios agentes** (workflows con grafos).

La clave pedagógica de todo el tutorial es esta: **MAF se construye literalmente encima de `IChatClient`**. No reemplaza lo que sabés; lo envuelve. El método estrella se llama `.AsAIAgent()` y hace exactamente lo que su nombre dice: agarra un cliente de chat y lo convierte en un agente.

## El linaje, para ubicarte

MAF es la fusión de dos proyectos previos de Microsoft:

- **Semantic Kernel** aportó lo "empresarial": manejo de estado, telemetría, middleware, type safety.
- **AutoGen** aportó las abstracciones simples para agentes y orquestación multi-agente.

MAF es el sucesor directo de ambos, escrito por los mismos equipos, y llegó a su versión 1.0 (APIs estables, soporte a largo plazo) en abril de 2026. Funciona igual en .NET y en Python; nosotros vamos en C#.

No te hace falta Azure para aprenderlo. Funciona con OpenAI, Azure OpenAI, GitHub Models, Anthropic (Claude), o modelos locales vía Ollama y Foundry Local. Cualquier cosa que exponga un `IChatClient` sirve.

## El modelo mental central: cuatro piezas

Antes de los ejemplos, fijate este mapa. Todo lo que sigue es una de estas cuatro cosas:

| Pieza | Qué es | El "a mano" que reemplaza |
|---|---|---|
| **`AIAgent`** | La unidad autónoma. Razona y actúa. | Tu loop ReAct entero. |
| **`AgentSession`** | El hilo de conversación. Memoria de corto plazo. | Tu `List<ChatMessage>` que ibas acumulando. |
| **`AIContextProvider`** | Inyecta contexto antes/después de cada turno. Memoria de largo plazo, RAG. | El `string` de "datos del usuario" que pegabas al system prompt. |
| **`Workflow`** | Un grafo de ejecutores conectados por aristas. Orquesta varios agentes. | El `if/else` con el que decidías a qué modelo llamar. |

Vamos a recorrerlas en orden de complejidad creciente.

## Nivel 1 — Tu primer agente

El "hola mundo". Acá lo importante no es lo que hace (cuenta un chiste), sino **ver la cadena de transformación**: SDK del proveedor → cliente de chat → agente.

```csharp
using OpenAI;
using Microsoft.Agents.AI;

var apiKey = Environment.GetEnvironmentVariable("OPENAI_API_KEY")
    ?? throw new InvalidOperationException("Falta OPENAI_API_KEY");

// 1. El SDK crudo del proveedor.
// 2. .GetChatClient(modelo) te da el sub-cliente del modelo.
// 3. .AsAIAgent(...) lo envuelve en un agente.
AIAgent agente = new OpenAIClient(apiKey)
    .GetChatClient("gpt-5.4-mini")
    .AsAIAgent(
        instructions: "Sos bueno contando chistes. Respondé en español rioplatense.",
        name: "Chistoso");

Console.WriteLine(await agente.RunAsync("Contame un chiste de piratas."));
```

Tres ideas para no perder de vista:

**`instructions` es el system prompt.** Lo que antes ponías como primer mensaje con `ChatRole.System`, ahora vive en el agente. Define su personalidad y sus reglas, y se aplica en cada turno automáticamente.

**`RunAsync` es el reemplazo de tu bucle.** Una sola llamada. Adentro, MAF arma el mensaje, llama al modelo, y si hubiera herramientas las gestionaría (lo vemos en el Nivel 2). Devolvés y listo.

**`AIAgent` es el tipo base abstracto.** Da igual si abajo hay OpenAI, Claude o un modelo local: el resto de tu código habla con `AIAgent` y no se entera del proveedor. Eso es lo que después permite armar orquestaciones agnósticas.

### Streaming

Si querés ver la respuesta token a token en vez de esperar el bloque completo:

```csharp
await foreach (var update in agente.RunStreamingAsync("Contame un chiste de piratas."))
{
    Console.Write(update);
}
```

Mismo agente, distinta forma de consumir. `RunAsync` espera todo; `RunStreamingAsync` te va dando pedazos.

## Nivel 2 — Darle herramientas

Acá es donde un agente deja de ser un chatbot. Una **herramienta** es una función de C# que el modelo puede decidir llamar. Vos no escribís "si pregunta por el clima, llamá a tal función": el modelo lo decide solo.

El porqué: el modelo no sabe el clima de Tucumán hoy, pero puede *darse cuenta* de que tiene una función que sí lo sabe, llamarla con el parámetro correcto, y usar el resultado para responder.

```csharp
using System.ComponentModel;
using OpenAI;
using Microsoft.Agents.AI;
using Microsoft.Extensions.AI;

// Una función común y corriente. Lo importante son los [Description].
[Description("Obtiene el clima para una ubicación dada.")]
static string ObtenerClima(
    [Description("La ciudad para la que se quiere el clima.")] string ciudad)
    => $"En {ciudad} está nublado con una máxima de 15°C.";

var apiKey = Environment.GetEnvironmentVariable("OPENAI_API_KEY")!;

AIAgent agente = new OpenAIClient(apiKey)
    .GetChatClient("gpt-5.4-mini")
    .AsAIAgent(
        instructions: "Sos un asistente útil.",
        tools: [AIFunctionFactory.Create(ObtenerClima)]);

Console.WriteLine(await agente.RunAsync("¿Cómo está el clima en Yerba Buena?"));
```

Lo que pasa adentro de ese único `RunAsync` es **exactamente tu loop ReAct**, pero MAF lo corre por vos:

1. Manda tu pregunta + la lista de herramientas al modelo.
2. El modelo responde: "quiero llamar a `ObtenerClima` con ciudad = Yerba Buena".
3. MAF ejecuta tu función de C#.
4. MAF mete el resultado de vuelta en la conversación.
5. Vuelve a llamar al modelo, que ahora redacta la respuesta final.

Vos escribiste *cero* líneas de "detectar pedido de tool / ejecutar / reinyectar". Esa es la diferencia.

### Por qué los `[Description]` no son opcionales

Los atributos `[Description]` son el manual de instrucciones de la herramienta *para el modelo*. El modelo no lee el cuerpo de tu función; lee el nombre, las descripciones y los tipos. Una descripción vaga lleva a que la herramienta se use mal o no se use. Pensalos como parte del prompt, no como documentación decorativa.

`AIFunctionFactory.Create(...)` es el puente: toma tu `Func`/método de C# y genera el esquema (nombre, parámetros, tipos, descripciones) que el modelo necesita para decidir. Es la misma fábrica de MEAI, así que cualquier herramienta que ya hayas definido para un `IChatClient` sirve acá tal cual.

## Nivel 3 — Conversaciones multi-turno con sesiones

Hasta ahora cada `RunAsync` es amnésico: no recuerda nada del anterior. Para una charla real necesitás que el agente sepa de qué venían hablando.

El porqué: cuando el usuario dice "ahora agregale emojis a *ese* chiste", el "ese" solo tiene sentido si hay memoria del turno anterior. Esa memoria de corto plazo es la **sesión**.

```csharp
AgentSession sesion = await agente.CreateSessionAsync();

Console.WriteLine(
    await agente.RunAsync("Contame un chiste de piratas.", sesion));

Console.WriteLine(
    await agente.RunAsync(
        "Ahora agregale emojis y contámelo con voz de loro pirata.",
        sesion));
```

La diferencia con el Nivel 1 es un solo parámetro: le pasás la `sesion` a cada `RunAsync`. La sesión va guardando el historial entre llamadas. El segundo turno "sabe" cuál chiste, porque la sesión lo conserva.

Acá la sesión reemplaza tu vieja `List<ChatMessage>` que ibas llenando a mano. Pero hace algo más, clave para producción:

### Serializar la sesión

Un servicio web es *stateless*: cada request puede caer en una instancia distinta del servidor, que no tiene la memoria en RAM. La solución es guardar el estado de la sesión (en una base, en Redis, donde sea) y recuperarlo después.

```csharp
// Guardás el estado (por ejemplo, en tu base de datos)
JsonElement estado = await agente.SerializeSessionAsync(sesion);

// Más tarde, en otro request, lo recuperás
var sesionRestaurada = await agente.DeserializeSessionAsync(estado);

Console.WriteLine(
    await agente.RunAsync("¿De qué estábamos hablando?", sesionRestaurada));
```

Esto es lo que permite que un agente "recuerde" una conversación que empezó hace horas, en otra instancia del servidor. La memoria vive afuera del proceso, no en una variable.

## Nivel 4 — Memoria de largo plazo con `AIContextProvider`

La sesión recuerda *esta* conversación. ¿Y si querés que el agente recuerde cosas del usuario **entre** conversaciones distintas? Su nombre, sus preferencias, lo que hablaron la semana pasada. O que, antes de responder, busque documentos relevantes en tu base vectorial (RAG).

Para eso está `AIContextProvider`. Es un objeto que se engancha en dos momentos del ciclo de vida de cada turno:

- **`ProvideAIContextAsync`** corre *antes* de cada interacción. Inyecta contexto extra (datos del usuario, documentos recuperados, instrucciones dinámicas).
- **`StoreAIContextAsync`** corre *después* de cada interacción. Es la oportunidad del agente de *aprender* de lo que acaba de pasar (extraer un dato y guardarlo).

El porqué de separar esto: desacoplás **qué recuerda el agente** de **cómo conversa**. La lógica de memoria vive en una clase aparte, y podés apilar varios providers (uno para preferencias, otro para historial, otro que hace RAG contra tu VectorData).

Ejemplo: un provider que extrae y recuerda el nombre del usuario.

```csharp
internal sealed class MemoriaUsuario : AIContextProvider
{
    private readonly ProviderSessionState<InfoUsuario> _estado;
    private readonly IChatClient _chatClient;

    public MemoriaUsuario(IChatClient chatClient)
    {
        this._estado = new ProviderSessionState<InfoUsuario>(
            _ => new InfoUsuario(),
            GetType().Name);
        this._chatClient = chatClient;
    }

    // DESPUÉS del turno: aprender. ¿Apareció el nombre? Lo guardo.
    protected override async ValueTask StoreAIContextAsync(
        InvokedContext context,
        CancellationToken cancellationToken = default)
    {
        var info = this._estado.GetOrInitializeState(context.Session);

        if (info.Nombre is null
            && context.RequestMessages.Any(m => m.Role == ChatRole.User))
        {
            var resultado = await this._chatClient.GetResponseAsync<InfoUsuario>(
                context.RequestMessages,
                new ChatOptions()
                {
                    Instructions = "Extraé el nombre del usuario del mensaje, si aparece."
                },
                cancellationToken: cancellationToken);

            info.Nombre ??= resultado.Result.Nombre;
        }

        this._estado.SaveState(context.Session, info);
    }

    // ANTES del turno: inyectar lo que ya sé.
    protected override ValueTask<AIContext> ProvideAIContextAsync(
        InvokingContext context,
        CancellationToken cancellationToken = default)
    {
        var info = this._estado.GetOrInitializeState(context.Session);

        var instrucciones = info.Nombre is null
            ? "Pedile el nombre al usuario."
            : $"El nombre del usuario es {info.Nombre}.";

        return new ValueTask<AIContext>(
            new AIContext { Instructions = instrucciones });
    }
}
```

Y lo enchufás al crear el agente:

```csharp
AIAgent agente = chatClient.AsAIAgent(new ChatClientAgentOptions()
{
    ChatOptions = new()
    {
        Instructions = "Sos un asistente amable. Siempre llamá al usuario por su nombre."
    },
    AIContextProviders = [new MemoriaUsuario(chatClient.AsIChatClient())]
});
```

Fijate el patrón: el provider *no* conversa. Solo decide qué meterle al contexto antes y qué guardar después. El agente conversa. Responsabilidades separadas.

Acá se cierra el círculo con lo que vimos de RAG y VectorData: un `AIContextProvider` que, en `ProvideAIContextAsync`, hace una búsqueda semántica en tu base vectorial y devuelve los documentos relevantes como contexto. Eso convierte el RAG manual en algo que pasa solo, en cada turno.

## Nivel 5 — Workflows: orquestar varios agentes

Un solo agente alcanza para mucho. Pero muchos problemas reales se resuelven mejor repartiendo el trabajo entre **agentes especializados** que colaboran. Para eso MAF tiene un sistema de **workflows basado en grafos**.

El vocabulario, que es lo central:

- **Ejecutor (executor):** una unidad de procesamiento. Puede ser un agente, o una función simple.
- **Arista (edge):** una conexión que define el flujo de datos. "La salida de A entra a B."
- **`WorkflowBuilder`:** el constructor con el que armás el grafo.

El porqué de pensarlo como grafo: en vez de un `if/else` enredado decidiendo a mano quién llama a quién, **declarás la topología** (quién se conecta con quién y bajo qué condición) y dejás que el framework ejecute el recorrido.

### El workflow más simple posible

Para entender el mecanismo sin distracciones, un workflow de dos ejecutores que ni siquiera usan IA: uno pasa a mayúsculas, otro invierte el texto.

```csharp
using Microsoft.Agents.AI.Workflows;

Func<string, string> aMayusculas = s => s.ToUpperInvariant();
var mayus = aMayusculas.BindAsExecutor("Mayusculas");
var invertir = new InvertirTextoExecutor();

// El builder arranca en el ejecutor inicial.
WorkflowBuilder builder = new(mayus);

// Conectás: salida de 'mayus' → entra a 'invertir'.
// Y declarás que la salida final del workflow viene de 'invertir'.
builder.AddEdge(mayus, invertir).WithOutputFrom(invertir);

var workflow = builder.Build();

// Lo corrés. La entrada "Hello, World!" recorre el grafo.
await using Run run = await InProcessExecution.RunAsync(workflow, "Hello, World!");

foreach (WorkflowEvent evt in run.NewEvents)
{
    if (evt is ExecutorCompletedEvent ec)
    {
        Console.WriteLine($"{ec.ExecutorId}: {ec.Data}");
    }
}
```

Lo que tenés que sacar de acá: **el dato fluye por las aristas**. Vos no llamás a cada ejecutor en orden; declarás el grafo (`AddEdge`) y `RunAsync` se encarga del recorrido. Los `WorkflowEvent` son cómo observás qué fue pasando paso a paso (útil para debugging y telemetría).

### Patrones que el grafo habilita

Con ese mismo mecanismo de ejecutores + aristas, MAF soporta los patrones clásicos de multi-agente:

- **Secuencial:** los agentes procesan en fila, la salida de uno alimenta al siguiente.
- **Concurrente:** se abre en abanico a varios agentes en paralelo (*fan-out*) y después se juntan los resultados (*fan-in*).
- **Ruteo condicional (hand-off):** se decide dinámicamente a qué agente mandar el trabajo según la salida del paso anterior.
- **Bucles de feedback:** el patrón escritor-crítico, donde uno produce y otro evalúa, repitiendo hasta que la calidad sea suficiente.
- **Sub-workflows:** componés workflows metiendo uno dentro de otro, jerárquicamente.

### El patrón escritor-crítico

Es uno de los más útiles y muestra el poder de las aristas condicionales. Un agente escribe (digamos, copy de marketing) y otro lo revisa. Si el crítico no lo aprueba, vuelve al escritor. Loop hasta que pase.

```csharp
WorkflowBuilder builder = new(agenteEscritor);

builder
    // El escritor manda su borrador al crítico.
    .AddEdge(agenteEscritor, agenteCritico)
    // Si NO está aprobado, vuelve al escritor para revisión.
    .AddEdge(agenteCritico, agenteEscritor, condition: r => !r.IsApproved)
    // Si SÍ está aprobado, esa es la salida del workflow.
    .WithOutputFrom(agenteCritico, condition: r => r.IsApproved);

var workflow = builder.Build();
```

La elegancia está en las **condiciones sobre las aristas**: `condition: r => !r.IsApproved`. La topología del grafo *es* la lógica de control. No hay un `while` escrito a mano; el ciclo emerge de cómo conectaste los nodos.

Un consejo de producción: ponele siempre un tope de iteraciones a estos bucles. Un crítico demasiado exigente puede mandar a revisar para siempre (y eso son tokens y plata).

## Nivel 6 — Humano en el loop

No todo lo que un agente quiere hacer debería hacerlo solo. Escribir en una base, mandar un mail, mover plata: ahí querés que un humano apruebe antes.

MAF soporta esto con un flujo de aprobación de herramientas, construido sobre dos tipos del modelo de contenido de MEAI: `FunctionApprovalRequestContent` y `FunctionApprovalResponseContent`.

El mecanismo conceptual:

1. El agente decide que quiere llamar a una herramienta sensible.
2. En vez de ejecutarla, **emite un pedido de aprobación y se frena**.
3. Tu código le muestra el pedido al usuario ("el agente quiere borrar 50 registros, ¿confirmás?").
4. La respuesta del usuario determina si la llamada procede o no.

Pensá los agentes como trabajadores especializados dirigidos por humanos a través del código. La autonomía es una herramienta, no un fin: la das donde es barata de equivocarse y la retenés donde es cara.

## Nivel 7 — Herramientas externas con MCP

Volvé un momento al Nivel 2. Ahí una herramienta era una función de C# tuya, envuelta con `AIFunctionFactory.Create(...)` y pasada en `tools: [...]`. Funciona perfecto mientras la capacidad viva en tu propio código.

¿Pero qué pasa cuando la capacidad vive *afuera*? Un servidor que sabe leer el filesystem, otro que habla con GitHub, otro que consulta una base corporativa, quizás escritos en Python o Rust por otro equipo. Antes de MCP, cada uno de esos era un wrapper a mano: leías su API, escribías el cliente, lo adaptabas a tool. Una integración distinta por cada sistema.

El **Model Context Protocol (MCP)** es el estándar que elimina ese trabajo repetido. Pensalo como una API universal para herramientas de agentes: en vez de construir una conexión a medida para cada servicio, el agente se conecta a un *endpoint MCP* que expone una lista de herramientas, y el agente las usa.

La idea central, y el motivo por el que esto encaja tan limpio en lo que ya sabés: **en MAF un servidor MCP no es una categoría especial de cosa, es simplemente otra fuente de herramientas.** Las tools que descubre de un servidor MCP se convierten automáticamente en objetos `AITool`, el mismo tipo que produce `AIFunctionFactory`. El agente no distingue el origen: una `AITool` es una `AITool`, venga de una función tuya o de un proceso externo que habla el protocolo. Por eso el lugar del código donde las enchufás es idéntico: `tools: [...]`.

### El paquete

MCP vive en su propio SDK, separado del de agentes. Es el SDK oficial de C#, mantenido en colaboración entre Microsoft, Anthropic y la organización del protocolo abierto MCP:

```bash
dotnet add package ModelContextProtocol --prerelease
```

### El patrón en tres pasos

El caso que más vas a usar en clase es un servidor **local por stdio**, porque no depende de Azure ni de ninguna nube: arrancás el servidor como un proceso hijo en tu propia máquina.

```csharp
using Microsoft.Agents.AI;
using Microsoft.Extensions.AI;
using ModelContextProtocol.Client;

// 1. Crear el cliente MCP. Levanta el servidor de filesystem como
//    proceso local vía npx. El último argumento acota a qué carpeta
//    puede acceder: ya estás poniendo un límite de seguridad.
await using var mcpClient = await McpClientFactory.CreateAsync(
    new StdioClientTransport(new()
    {
        Name = "Filesystem",
        Command = "npx",
        Arguments = ["-y", "@modelcontextprotocol/server-filesystem", "/ruta/permitida"]
    }));

// 2. Descubrir las herramientas que expone el servidor (el "handshake").
var mcpTools = await mcpClient.ListToolsAsync();

// 3. Crear el agente pasándole esas tools, igual que cualquier otra.
var apiKey = Environment.GetEnvironmentVariable("OPENAI_API_KEY")!;
AIAgent agente = new OpenAIClient(apiKey)
    .GetChatClient("gpt-5.4-mini")
    .AsAIAgent(
        instructions: "Usá las herramientas disponibles para responder.",
        tools: [.. mcpTools.Cast<AITool>()]);

Console.WriteLine(await agente.RunAsync("¿Qué archivos hay en la carpeta?"));
```

Los dos momentos del protocolo que importan conceptualmente:

- **Discovery (`ListToolsAsync`):** el cliente le pregunta al servidor "¿qué sabés hacer?" y recibe la lista de tools con sus descripciones. Es el equivalente externo de los `[Description]` del Nivel 2.
- **Invocación:** cuando el modelo decide usar una tool, MAF rutea la llamada al servidor por el canal stdio, espera el resultado y lo reinyecta. Es el mismo loop ReAct de siempre, pero el paso "ejecutar la tool" cruza un límite de proceso.

El `await using` no es decorativo: asegura que la conexión se cierre bien al salir de scope. Como el servidor local es un proceso hijo, querés que se termine prolijamente y no quede colgado.

### Los dos transportes

Según dónde viva el servidor, cambia el transporte:

- **stdio** (`StdioClientTransport`): el servidor es un proceso local que arrancás vos. Ideal para filesystem, git, bases locales. Es el del ejemplo.
- **SSE / HTTP** (`SseClientTransport`): el servidor es remoto, ya corriendo en un endpoint. Por ejemplo, el endpoint MCP de Microsoft Learn (`https://learn.microsoft.com/api/mcp`), que le da al agente la capacidad de buscar en la documentación de Microsoft. Mismo patrón de tres pasos, solo cambia cómo construís el transporte.

### MCP va en los dos sentidos

Hasta acá tu agente *consume* tools MCP. Pero también podés **exponer un agente MAF entero como una tool MCP**, para que cualquier cliente compatible lo use. El truco encadena dos ideas: primero convertís el agente en una `AIFunction` con `.AsAIFunction()` (que de paso es cómo un agente llama a otro agente como si fuera una función), y después envolvés esa función como tool MCP y la servís por HTTP. Construís el agente una vez, y cualquier cliente MCP del mundo puede usarlo.

### Criterio de producción (no es solo sintaxis)

Dos cosas que conviene que los alumnos internalicen, porque son las que distinguen un juguete de algo desplegable:

**Acotá la superficie de tools.** Un servidor MCP puede exponer muchísimas herramientas, y eso *no* significa que tu agente deba recibirlas todas. Más tools significa más descripciones enviadas al modelo (más tokens), más chances de que elija la equivocada, y más superficie que auditar. La regla es la misma que con tools locales: exponé el conjunto más chico que resuelva la tarea, y filtrá antes de que las tools lleguen al modelo.

**MCP facilita las integraciones, no las hace seguras solo.** El protocolo no es la capa de seguridad. Tratá a un servidor MCP como cualquier otra dependencia de integración: no conectes servidores random a un agente de producción, y no asumas que por hablar MCP ya es confiable. En particular, las credenciales van *fuera* del prompt: nunca metas API keys ni tokens OAuth en las instrucciones del agente. Para servidores remotos, lo correcto es pasarlas como headers por cada run, donde quedan disponibles solo para esa ejecución y no se persisten.

> **Nota de versión:** el paquete `ModelContextProtocol` está en preview y su superficie de API se mueve rápido mientras madura la especificación. Pineá una versión concreta y seguí el repo oficial del SDK de MCP para .NET; esperá cambios de API entre previews.

## Cómo encaja todo (el cierre)

La idea de "bloques que componen" es lo que hace valioso a MAF. Repasando la pila completa:

1. **MEAI (`IChatClient`)** es el cimiento: la interfaz universal para hablarle a cualquier modelo.
2. **VectorData** habilita RAG: tus agentes buscan en la base de conocimiento de tu organización con búsqueda semántica.
3. **Agent Framework** orquesta todo: los agentes usan `IChatClient` por debajo, incorporan búsqueda vectorial a través de context providers, y se coordinan con workflows.

Y la progresión que recorriste, que es la que conviene que tengan internalizada:

| Nivel | Pieza | Qué agregó |
|---|---|---|
| 1 | `AsAIAgent` + `RunAsync` | El agente y su bucle de ejecución. |
| 2 | `AIFunctionFactory` + `[Description]` | Acción: el agente usa herramientas. |
| 3 | `AgentSession` | Memoria de corto plazo (una conversación). |
| 4 | `AIContextProvider` | Memoria de largo plazo y RAG (entre conversaciones). |
| 5 | `WorkflowBuilder` + ejecutores + aristas | Orquestación de varios agentes. |
| 6 | `FunctionApprovalRequestContent` | Control humano sobre acciones sensibles. |
| 7 | `McpClientFactory` + `ListToolsAsync` | Herramientas externas vía MCP (estándar abierto). |

El hilo conductor, una vez más: **nada de esto es magia**. Cada pieza reemplaza un andamiaje que ya sabés escribir a mano. MAF te lo da hecho, probado y componible, para que vos pongas la atención en la *lógica del agente* y no en la plomería.
